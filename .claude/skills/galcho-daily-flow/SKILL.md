# ギャル庁 毎日の制作フロー親スキル

ギャル庁の毎日の記事制作を回す時の全体マップ。各ステップで個別スキルを呼ぶ。

## 🗺️ 全体フロー

```
Step1 (User)   ネタ提供＋aashi提供
   ↓
Step1.5(Main)  🔍メインが新記事ネタの裏取り（WebSearch）→ 結果をサブエージェントに渡す
   ↓
Step2 (Agent)  ⚡記事生成＋日常ツイート＋既存記事の加筆（サブエージェント並列）
   ↓
Step3 (Agent)  アフィ取得（順次・必要な記事のみ）
   ↓
Step4 (Agent)  ビルド確認 → commit → push
   ↓
Step5 (Agent)  ★記事URL確定 → プロモツイート文生成
   ↓
Step6 (Agent)  ⏰公開待ち（Cron 7/11/17 + Pages リビルド1〜2分）
   ↓
Step7 (Agent)  Xライブツリー投稿（公開済み記事のみ・順次）
   ↓
Step8 (Agent)  tweets-schedule.md 更新
```

## 📝 Step1｜ネタ選定＆素材提供（★User主導）

- ネタは**ユーザーがチャットで渡す**（エージェントが勝手にネタ収集しない）
- **aashi（語り手コメント）はユーザーの人間味パート**:
  - AIっぽさを消す部分
  - エージェントは**勝手に作り込まない・書き換えない**
  - 提供がなければ user に確認

## 🔍 Step1.5｜裏取り（ファクトチェック）の分担（★ここで決まる・2026-09-27確立）

**裏取りを誰がやるかは作業の種類で変える。** 混ぜると重複検索でトークンが溶けるか、事実がバラつく。

| 作業 | 裏取りするのは | 理由 |
|---|---|---|
| **その日の新記事の整形** | **メインエージェントが先にまとめて**（結果を指示文で渡す） | 複数記事が同じ出来事を扱うことが多く（例：米中首脳会談の一連の記事）、各体が同じ検索を繰り返すのは無駄。かつ体ごとに事実がバラつく |
| **既存記事の加筆** | **各サブエージェントが自分で** | 記事ごとに必要な情報が違い、何を足すか決めながら調べる必要がある（→ [[galcho-rewrite]]） |

### 新記事＝メインが先に裏取りして渡す

1. ユーザーからもらった素材の**日付・数字・固有名詞・発言**をメインが WebSearch で確認する
2. 確認結果を「**裏取り結果**」としてサブエージェントの指示文に**そのまま書き込む**
3. 指示文に必ずこの一文を入れる：
   > **この裏取り結果を優先すること。素材と食い違う場合は裏取り結果に合わせる。**
4. 同じ出来事を扱う記事が複数あるときは、**1回の裏取り結果を全体で共有**する（各体に再検索させない）

### 既存記事の加筆＝サブエージェントが自分で裏取り

- 各体が担当記事に必要な裏取りを自分で WebSearch する
- **ただし1体あたりの担当は3本まで**（2026-09-27の実測で1体17〜21万トークン消費。担当を増やすと膨らむ）
- 詳細は [[galcho-rewrite]]（足す中身・厳守事項・訂正記載）

### どちらの場合も共通（厳守）

- **確認できない数字・固有名詞は書かない**、または「〜とされてる」「〜が多い」に弱める
- **記事の公開日より後の出来事を足さない**（日付は絶対表記。「今日」「昨日」は使わない）
- **裏取りで既存記事の誤りが見つかったら、訂正して記事末尾に明記する**（手順は [[galcho-rewrite]] の「訂正を記事に明記する」）

## ⚡ Step2｜記事＋日常ツイート＋加筆（並列で爆速）

### 並列で投入
- **サブエージェントで複数記事を並列生成**（テキスト生成は並列OK）
- **同じフェーズで日常ツイート（リンクなし）も並列で作る**（記事URLに依存しないので待つ必要なし）
- **同じフェーズで既存記事の加筆も1体ぶん走らせる**（→ 下の「加筆枠」）
- 朝7:00 / 昼11:00 / 夕17:00 の publishDate で予約配置
- **その場で今すぐ公開する記事だけは publishDate を「現在時刻マイナス5分」にする**（→ Step4 の「即時公開のときは publishDate を…」）

### 参照スキル
- [[galcho-article-format]] — front matter + HTML パーツの整形
- [[galcho-rewrite]] — 加筆のやり方（足す中身・厳守事項・lastmod・検証）

### 並列指示テンプレ
```
記事3本＋日常ツイート3本＋既存記事の加筆2〜3本を並列生成する。
- 記事1（slug-a, 朝7:00公開, ネタA ＋メインの裏取り結果を添付）
- 記事2（slug-b, 昼11:00公開, ネタB ＋メインの裏取り結果を添付）
- 記事3（slug-c, 夕17:00公開, ネタC ＋メインの裏取り結果を添付）
- 日常ツイートx3（夜21:00公開・記事URL依存なし）
- 加筆x2〜3（既存記事・1体あたり最大3本・裏取りは各体が自分でやる・→ [[galcho-rewrite]]）
```

**★新記事を投げる指示文には必ず「裏取り結果」を貼る**（→ Step1.5）。
記事整形のサブエージェントに自分で WebSearch させない（重複検索・事実バラつきの原因）。

## ➕ Step2b｜既存記事の加筆枠（毎日2〜3本・記事生成と同時に走らせる）

毎日の新記事生成と**同じ並列フェーズで、既存記事の加筆を1体ぶん**投入する。**1日2〜3本が目安**。

- 新記事の整形と加筆は**別ファイルを触るので衝突しない**
- どのみち一番遅い1体を待つフェーズなので、**待ち時間はほぼ増えない**
- **加筆は各体が自分で裏取りする**（新記事と逆。→ Step1.5 の分担表）
- **1体あたりの担当は最大3本**（トークン消費を抑えるため）
- 加筆のやり方そのものは [[galcho-rewrite]] を参照（ここには重複して書かない）

### 加筆する記事の選び方（優先順）
1. **その日の新記事と関連する古い記事** — 相互リンクでテーマのかたまりを作る（例：台風の新記事を書く日は、過去の台風記事を加筆して相互リンク）
2. **本文が短い順** — 1,000字未満は2026-09-27時点で解消済み。次の山は**1,000〜2,000字の147本**
3. **Search Console で「表示回数はあるのにクリックが少ない」記事** — データが溜まる2026年10月以降に使える手

### 後始末
- 加筆した記事には **`lastmod` を付ける**（更新日がサイト・サイトマップ・構造化データに出る）
- 加筆分も Step4 の commit & push に一緒に乗せる
- **任意**：加筆した記事は X で「情報を足して更新した」形で再プロモしてもOK。ネタが少ない日の埋め草になる

## 🛍️ Step3｜アフィ取得（順次・必要な記事のみ）

- 商品が**自然に紐づく記事のみ**（ゲーム/書籍/グッズ/電化製品）
- 無理に全記事に付けない
- **禁止ジャンル除外**: FX/投資/ギャンブル/情報商材/健康詐欺

### 参照スキル
- [[galcho-moshimo-affi]] — JS DOM操作でスニペット取得・捏造防止

### 順次の理由
- ブラウザ操作は並列不可（同一セッション競合）
- 1記事ずつ完了させてから次へ

## 🚀 Step4｜ビルド確認 → commit → push

```powershell
# 1. Hugo ビルド確認（future-dated 含む場合は --buildFuture）
cd C:\Users\circl\Desktop\Code\gal\site
hugo --minify
# または future-dated テスト
hugo --buildFuture --destination=/tmp/test-build

# 2. commit & push
git add .
git commit -m "feat: ◯◯記事追加（YYYY-MM-DD公開分N本）"
git push
```

- **push 完了で記事 slug = URL が確定**する
- これより前にツイート文（記事URL付き）を確定させると 404 リスク

### ★即時公開のときは publishDate を「現在時刻マイナス5分」にする（2026-09-27の事故）

定時枠（7:00/11:00/17:00）じゃなく**その場で今すぐ公開する記事**は、publishDate を
**必ず現在時刻より5分前**にする。「ちょうど今」はダメ。

- **事故内容（2026-09-27）**：publishDate を「ちょうど今」（23:25）にして push したら、Cloudflare のビルドが走り始めた時点ではまだ publishDate が数十秒**先**だったため、`buildFuture = false` の設定で**記事が丸ごとビルドから除外された**。ビルド自体は成功しているのにサイトに記事が出ない、という分かりにくい形で**15分ロス**
- **原因**：push → Cloudflare Pages のビルド開始までに数十秒〜1分かかる。その間に publishDate を追い越していないと「未来の記事」と判定される
- **対策**：現在の JST を **PowerShell の `Get-Date` で確認**してから、そこから5分引いた時刻を publishDate にする（**Bash の `date` は UTC なので使わない**）
- **症状が出たときの直し方**：publishDate が既に過去になっていることを確認したうえで、空コミットを push して再ビルドをかける

```powershell
Get-Date                      # 現在のJSTを確認（Bashのdateは使わない）
git commit --allow-empty -m "chore: rebuild"
git push
```

- **確認方法**：200 が返るまで待つ。404 のままならビルドに入っていない

```bash
curl -s -o /dev/null -w '%{http_code}' https://gal-cho.com/posts/{slug}/
```

- なお**定時枠（朝7:00 / 昼11:00 / 夕17:00）の予約公開ではこの問題は起きない**（Workers Cron が時刻を過ぎた後にリビルドをかけるため、ビルド時点で publishDate は必ず過去）

## 📝 Step5｜プロモツイート文生成

- **記事 push 完了後**に作る（URL確定済み）
- 各記事の front matter `tweet:` フィールドを基にする
- 朝/昼/夕の3本（記事プロモ）

### ルール
- 本文に記事URLを貼らない（2026年X外部リンク格下げペナルティ回避）
- 本文末尾に「詳しくはリプから👇」誘導
- ハッシュタグは 1〜2個まで（基本 `#ギャル庁` ＋ジャンル1個）
- 140字以内

## ⏰ Step6｜公開待ち

- Workers Cron が**7:00 / 11:00 / 17:00 JST**に自動公開
- Cloudflare Pages リビルド1〜2分
- リビルド完了後に URL がライブになる
- **未公開記事をプロモするとリプの URL が 404** → 必ず公開後
- 定時枠はこの流れなので publishDate の追い越し事故は起きない。**即時公開だけ別扱い**（→ Step4 の「即時公開のときは publishDate を…」）

### キャッチアップ方式（時短）
- セッション時点で**既に公開済み**の記事を1パスでまとめて投稿
- 同日でも後の時間帯（未公開）の記事は次セッション送り
- 公開待ちでブラウザを何度も往復しない

## ⚡ 時短の鉄則

| 工程 | 並列? | 理由 |
|---|---|---|
| 新記事ネタの裏取り | ❌ メインが先に1回 | 重複検索と事実バラつきを防ぐ（→ Step1.5） |
| 記事生成 | ✅ 並列 | テキスト生成・サブエージェント可（裏取り結果を渡す） |
| 日常ツイート生成 | ✅ 並列 | URL依存なし・記事生成と同フェーズで |
| 既存記事の加筆 | ✅ 並列 | 別ファイルなので新記事と衝突しない・待ち時間ほぼ増えない |
| プロモツイート文 | ⚠️ push後 | URL依存（記事push完了が前提） |
| アフィ取得 | ❌ 順次 | 同一ブラウザセッション競合 |
| X投稿 | ❌ 順次 | 同上 |

**「記事を一気に作る」部分にサブエージェントを投入してトータル時間を短縮する**のがコツ。

## 📅 日常ツイートの予約は当日分のみ（2026-05-25確定）

- 数日先まで先回り予約しない（X 予約UIの作業時間が膨らむため）
- 毎日セッションがある前提で、その日のセッションで当日21:00分を予約 or ライブ投稿で十分
- 当日同日なら日付ドロップを触らず時刻だけ合わせれば爆速
